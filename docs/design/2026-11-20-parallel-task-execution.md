# 独立任务并行执行：现状、收益测算与方案

问题：一件 Run 的计划是一张任务 DAG，但任务一个接一个执行，互相独立的任务也要排队。并行能缩短多长时间，要改多少，值不值得现在做？

## 0. 结论

- **不同 Run 之间已经并行。** 生产上每件 Run 是一个独立的 Temporal workflow，没有并发上限；对话里的每个任务各开一件 Run，所以"同时做几件事"现在就成立。生产记录里最多 4 件 Run 同时在跑，343 件里有 51 件和别的 Run 时间重叠。
- **一件 Run 内部并行，收益小，改动大。** 生产上 188 件可测量的多任务 Run 中，只有 24 件（13%）有可以同时跑的任务；全部并行后共省约 1.1 小时，占任务总耗时 21 小时的 5%。对这 24 件，中位数每件省约 100 秒，约占整件 Run 的 17%。其中 15 件是 Project Pulse，而 #237 之后 Project Pulse 只规划一个任务，这部分收益已经没有了。
- 要在一件 Run 里并行，必须拆掉"同一时间只有一个模型调用"这条贯穿引擎的不变量（第 3 节），并修改 Temporal workflow，风险集中在恢复、对账和回放。
- **建议：现在不改引擎（方案 A）**，先加一项低成本的测量，在迁移和 Grok Bot 对齐的真实负载上看计划形状；达到第 5 节的条件再做方案 B（同一 Run 内多条执行通道），先限 2 条。方案 C（拆成子 Run）不推荐。

## 1. 现状

### 1.1 一件 Run 内：严格串行

| 环节 | 位置 | 行为 |
|---|---|---|
| 推进入口 | `src/runtime/engine.ts:1901` `advance` | 进程内 `active` 集合保证同一 Run 同时只有一次推进；有 `started` 的调用就不推进（1906 行） |
| 选任务 | `engine.ts:2691` | 取第一个依赖已满足、尚未成功的节点，一次只取一个 |
| 模型调用预留 | `engine.ts:2279`、`2282` | 预留时要求没有别的 `started` 调用，且调用数与读到的快照一致。这既是"一次一个调用"的规则，也是防止两个引擎用旧快照重复调用的乐观锁 |
| 单数状态 | `contracts.ts:427`、`460`、`486` | `pendingTool`、`pendingDelegation`、`actionApproval`、`resumeModelCallId` 都是每件 Run 一个 |
| 时间预算 | `engine.ts:2217` | 每次调用按"剩余任务数"平分剩余的模型时间预算，默认任务依次执行 |
| Temporal | `src/temporal/workflows.ts:42`、`worker.ts` | 每件 Run 一个 workflow，循环调用 `advanceRun` activity，一次一个；activity 调用 API 的 `/internal/runs/:id/advance`，引擎实际在 API 进程里运行 |
| 电脑 | `local-tools.ts`、`docker-sandbox.ts` | 每件 Run 一台机器，工具调用依次执行 |

一次 `advance` 只做一件事：一次模型调用，或执行一个待办工具，或一次委派。任务 A 等工具时，任务 B 也只能等。

### 1.2 不同 Run 之间：已经并行

- `src/runtime/dispatcher.ts` 的 `notifyTemporalRunWorkflow` 为每件 Run 启动或唤醒自己的 workflow；worker 没有设置 activity 并发上限，使用 SDK 默认值。
- 对话里新建的每个任务、任务调度器（`task-scheduler.ts`）为计划节点创建的每件 Run 都是独立 Run，互不等待。
- `schedulingPriority` 只影响本地开发用的 `LocalRunDispatcher` 的排队顺序，生产的 Temporal 不受它限制。
- 生产测量（`aeeis_run_events` 中模型调用与工具完成事件的起止时间）：最多同时 4 件 Run，343 件中 51 件与其他 Run 重叠。

所以用户层面"同时交给 Bot 几件独立的事"已经是并行的。本设计只讨论一件 Run 内部。

## 2. 生产数据：计划形状与可省时间

方法：在生产 API 容器里用只读事务读取全部 346 件 Run，在内存中解密，只输出统计数字。每个任务的耗时取它第一次执行调用开始到最后一次执行调用结束（期间包括工具和委派）。"可省时间"＝任务耗时之和 − 按 DAG 依赖计算的关键路径长度，即假设并行数不受限、模型和工具不会因并行变慢时的上限。

| 项 | 数值 |
|---|---|
| 有计划的 Run | 326 |
| 多于一个任务 | 306 |
| 所有任务都跑过、可测量 | 188 |
| 任务数分布 | 2 个：79；3 个：61；4 个：43；5–6 个：5 |
| 有可同时执行的任务（DAG 某一层宽度 > 1） | 24（13%） |
| 其中 Project Pulse / 填 PDF / 其他 | 15 / 7 / 2 |
| 任务总耗时 | 21.0 小时 |
| 全部并行可省 | 1.06 小时（5%） |
| 这 24 件：可省中位数 | 约 102 秒，占整件 Run 约 17%（P75：22%） |
| 这 24 件：整件 Run 中位耗时 | 约 600 秒 |
| 收益最大的一件 | 4 个任务、宽 3：任务耗时 1078 秒 → 关键路径 544 秒 |

另外两点：

- 这些 Run 绝大多数来自 10 月的评测和试用；11 月以来生产上新的多任务 Run 很少，数据代表的是评测负载。
- 规划提示词要求"研究任务 + 依赖全部研究任务的最终汇总"（`engine.ts:634`），这种形状本来就有宽度；实际 87% 的计划仍是一条链，因为模型通常把后一步写成依赖前一步。

## 3. 一件 Run 内并行要改什么

"同时只有一个调用"不是一个开关，下面每一处都依赖它：

1. **调用预留与乐观锁**（`engine.ts:2279–2282`）。要改成按任务的通道：每条通道最多一个 `started` 调用，用通道内调用数或 Run 的 revision 做比较，不能再用全 Run 的调用数。
2. **对账与恢复**。`resumeModelCallId` 是单数，`reconcileModelCall`、`recoverRun`、`model.unknown` 的处理都假设只有一个结果不明的调用。要改成按调用 ID 对账；任何一个调用结果不明时，整件 Run 停下等对账（与现在一样），其他通道不再发起新调用。
3. **单数待办状态**。`pendingTool` / `pendingDelegation` / `actionApproval` 要改成按任务存放，或者规定同一时间只有一条通道可以有待办工具。后者改动小得多，但工具密集的任务收益也就少了。
4. **预算**。调用数上限、token 和金额预算、全局预算账本现在在预留时逐次检查。两条通道同时预留会各自看到"还剩一次"。预留必须在同一事务里检查并占用；`allocateModelCallTimeout` 也要改成按关键路径而不是任务数分配时间。
5. **需要人参与的暂停**。提问（`needs_input`）、动作审批、暂停和取消都作用于整件 Run。一条通道要提问时，另一条通道正在进行的调用要么等它完成再暂停，要么丢弃结果；需要定一个规则并写进事件。
6. **工作记忆压缩**（`compactWorkingMemory`）。压缩会改写所有任务看到的观察记录，必须独占：压缩期间其他通道不能发起调用。
7. **电脑与工具**。同一台机器上两个任务同时写文件或跑命令会互相干扰。最简单的规则：用到电脑的任务不并行，只并行只读来源工具和纯模型的任务。
8. **Temporal workflow**。现在每轮只调用一次 `advanceRun(runId)`。并行要改成每轮为每条可推进的通道各发一个 activity（`advanceRun(runId, taskId)`），等其中任意一个返回再决定下一轮；必须放在新的 `patched()` 分支后，保证已有 history 能回放，并且要经过部署时的回放门禁。
9. **事件与界面**。事件序号仍然全 Run 唯一，但两个任务的事件会交错出现；任务视图和调试包要按 `taskId` 分组，不能假设"当前任务"只有一个。
10. **评审与产出**。评审仍在所有任务完成后进行，不受影响；终端任务的产物类型判断（`engine.ts` 中 `terminal`）也不变。

## 4. 方案

### 方案 A：不改引擎，只改规划并保留跨 Run 并行（建议现在做）

- 已经做了：#237 让 Project Pulse 只规划一个任务，避免写多份完整报告。
- 新增一项测量（小改动）：每件 Run 结束时记一条 `plan.parallelism` 事件，内容是任务数、DAG 最大宽度、各任务耗时和按第 2 节方法算出的可省毫秒数。之后用一条 SQL 就能看真实负载上的收益，不用再解密整份 Run。
- 成本：约半天，含测试。风险：几乎没有，只多一条事件。

### 方案 B：同一 Run 内多条执行通道（条件满足后再做）

- 按第 3 节改造，通过 `AEEIS_RUN_PARALLEL_TASKS`（默认 `1`，即现在的行为）开启，先只允许 `2`。
- 第一版的范围：
  - 只并行不使用电脑的任务；
  - 同一时间最多一个待办工具或委派；
  - 任何结果不明的调用、提问、审批、压缩都让整件 Run 回到单通道。
- 实施顺序：
  1. 把调用预留和预算检查改成按通道、在同一事务里占用（行为不变，单通道）；
  2. 对账和恢复改成按调用 ID；
  3. 调度选出最多 N 个就绪任务；
  4. 加上 Temporal 新分支和回放测试；
  5. 打开开关，用评测里有宽度的计划做前后对比。
- 测试：同一 Run 两条通道同时预留时预算只够一次；两条通道之一结果不明后的恢复；进程在两个调用之间崩溃；旧 history 回放；提问与另一通道进行中的调用。
- 成本：约 2–3 周，主要在恢复和回放测试；`engine.ts` 已有 4700 行，`advance`、`call`、`execute`、`executePendingTool`、`recoverRun`、`reconcileModelCall` 都要动。
- 收益：按第 2 节的数据，有宽度的计划平均快约 17%，对全部负载约 5%。

### 方案 C：把独立分支拆成子 Run（不推荐）

- 规划后把互不依赖的分支各自交给一件子 Run（已有 `trusted.lineage` 派生机制），利用现成的跨 Run 并行，最后在父 Run 里汇总。
- 不用改"一次一个调用"的不变量，但新增的问题更多：证据和产物要跨 Run 引用并校验来源；预算要在父子之间切分；审批、提问和取消要跨 Run 传递；用户会看到多出来的 Run。为 5% 的收益不划算。

## 5. 什么时候再做方案 B

满足以下任一条件时重新评估：

- 方案 A 的事件显示，最近 30 天完成的多任务 Run 中，有宽度的超过 25%，且这些 Run 的可省时间中位数超过 60 秒；
- Grok Bot 对齐的验收任务里，有用户明确在等、且可以同时进行的多步任务（例如同时查几个来源再汇总），并且单靠调整规划无法缩短。
