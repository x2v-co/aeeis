# 会自己行动的 Bot

多 Bot 团队交互设计（2026-10-21）的核心承诺是：给一支团队发消息，入口 Bot 接话、拆活，专家 Bot 互相交接，人只在需要决定时出现。现在频道、任务板、交接卡、工作室都已经在，但每个 Bot 都「不会自己回复」：话送到了，工作要人来开 Run。本文把剩下的这一块补上，按 Grok Bot 的方式：**发消息就是派活，Bot 之间看得见地交接，人只做决定。**

## 1. 范围

1. **Bot 回复。** 入口 Bot（AEEIS）接没有点名的话；被 @ 的成员自己回复；私聊里对方回复。
2. **Bot 提议任务。** 回复里可以提一件事，落到任务板上，等人看见；按这个 Bot 的自主程度决定是否直接开工。
3. **交接在侧线程里谈。** 一件事交给另一个 Bot 时，任务卡先留在原处；两个 Bot 在侧线程（Bot 之间的私聊）里谈，对方接受才转过去，谈不拢就上报给人。
4. **连续失败两次改派。** 同一件事最近两次 Run 都失败，AEEIS 作为 PM 找另一位成员接手，走同样的交接。
5. **界面。** 群里能看出哪句是 Bot 自己说的；任务板上有「提议」和「交接中」；Bot 档案里能看到它的侧线程，默认折叠；每个 Bot 有自主程度设置。

不在范围：示范录制、工作台接管、关系网视图、模型路由（前门仍按规则路由）。

## 2. 谁回复（服务端规则）

和浏览器里的送达规则一致，回复只多一层「一个声音」：

| 说话人 | 房间 | 谁回复 |
|---|---|---|
| 人 | 群聊，点名了成员（`@名字`） | 被点名的成员，每人一条，最多 3 位 |
| 人 | 群聊，没点名、@AEEIS、@所有人、@团队 | AEEIS 一条（入口，一个声音） |
| 人 | 私聊 | 私聊里的那位 |
| Bot | 任何 | 没有人回复。Bot 之间的来回只在侧线程里 |

- 只回复 `message` 类型、`publish` 的事件；回执、任务动作、修订和撤回不触发。
- 自主程度为「只记录」的 Bot 不回复（保持现状）；外部准入的 Agent 不由 AEEIS 代答。
- 每条回复以房间主人代 Bot 发言的既有路径写入（`actor: agent`），幂等键 `bot-reply:<触发事件>:<bot>`，引用触发事件。失败写一条系统回执「X 这次没有回复：原因」，同样幂等，不反复重试。
- 回复在服务端后台进行；进程重启后，一个泵会补上最近 10 分钟里既没有回复也没有失败回执的消息。

## 3. Bot 怎么想

一次模型调用，走全局预算（和生成背景相同的预留、结算、结果不明标记）。输入：

- 这个 Bot 的名字、角色、背景；它的常驻嘱咐（来自生活线程）；频道的团队规则；
- 名册（名字、角色、当前在做几件）；
- 最近 30 条群消息，**标为不可信资料**；
- 这条消息和说话人。

输出：`{ reply, proposeTask?: { title, reason, for? }, handoff?: { to, note } }`。

规则写进系统提示：只讨论，不声称已经做了没做的事；不能调用工具；回复简短；要做事就提一件任务；别人更合适就交接给名册里的人。输出不合格就当作失败，写失败回执。

## 4. 提议任务

- 提议的事记在**执行它的那个 Bot**的生活线程上：AEEIS 可以 `for` 另一位成员；其他 Bot 只能给自己提。
- 群里写一条回执引用这件事（任务板据此出卡），再写任务动作 `propose`。卡片显示「提议 · 谁提的 · 理由」。
- 人可以「采纳」（`adopt`）或「不要」（`cancel`，写原因）。
- **自主程度**（Bot 档案里设置，默认「回复，提议等我」）：

| 自主程度 | 回复 | 提议之后 |
|---|---|---|
| 只记录 | 不回复 | — |
| 回复，提议等我 | 回复 | 等人采纳；采纳后由人开 Run |
| 自动 | 回复 | 直接开 Run，审批档位 `auto` |
| 放手 | 回复 | 直接开 Run，审批档位 `yolo` |

Bot 开的 Run 的来源是 `agent`，所以第 2 项的规则仍然管着它：写操作在 `auto` 下问人，在 `yolo` 下拒绝。每个 Bot 进行中的事受任务板 WIP（3 件）限制，超过就只提议不开工。

## 5. 交接与侧线程

- 发起：Bot 回复里的 `handoff`（对象是这条回复提议的那件事），或人在任务板上点「交给」（新的 `offer`）。卡片显示「交接中 · A → B」，任务仍归 A。
- 侧线程：A 和 B 之间的一间房（描述为「侧线程」），房间主人是频道主人，成员是两个 Bot。只在 Bot 档案里能看到，群聊和入口列表不显示。一对 Bot 共用一条侧线程。
- 来回：B 先说（接受 / 拒绝 / 继续谈）；A 回应（坚持 / 撤回 / 继续谈）；轮流，每轮一次模型调用。
- 结束：
  - B 接受 → 群里写 `transfer`，任务转给 B；B 的自主程度为自动或放手时，在原任务上开一次 Run。
  - B 拒绝或 A 撤回 → 写 `decline`，任务留在 A，群里一句结论。
  - 谈满 8 轮（`AEEIS_BOT_HANDOFF_MAX_TURNS`，最多 20）或预算用完仍没有结论 → 写 `block`，原因「交接谈不拢」，进收件箱。
- 原设计说「不设轮数上限，消息写满或预算用尽才停」。这里先设一个默认 8 轮、可调的上限，避免一对 Bot 在没有预算限制的部署里一直谈下去。

原设计写的是「走 Debate」。现有的 Debate 是带主持人、裁决和论点引用的多模型辩论，用来评判观点；交接只需要两方的往来记录，所以用侧线程房间承载，记录同样只追加、可追溯。

## 6. 连续失败改派

- 一个泵每分钟看一遍活跃群聊的任务板：一件事最近两次 Run 都是 `failed`，且这次失败还没有改派过（幂等键含最近的 Run id）。
- AEEIS 在群里说一句，然后按名册选人：不是当前负责人、进行中最少、自主程度不是只记录；没有合适的人就写 `block`，上报给人。
- 选到人就以 AEEIS 为发起方走第 5 节的交接。

## 7. 新的任务动作

| 动作 | 谁写 | 含义 |
|---|---|---|
| `propose` | 服务端（代 Bot） | 这件是某位 Bot 提议的 |
| `adopt` | 人 | 采纳提议 |
| `offer` | 服务端或人 | 交给某位，等对方接受 |
| `decline` | 服务端 | 对方没接（拒绝或发起方撤回），原因 |

`transfer`、`block`、`cancel` 沿用。交接中再 `offer` 给第三位会被拒绝；`transfer` 会清掉交接中。

## 8. 成本和噪声

- 每条人发的群消息最多 3 次回复调用；Bot 的话不触发回复；侧线程每轮一次调用，有轮数上限。
- 全局预算用尽时，回复失败并写失败回执，交接上报给人。
- `AEEIS_BOT_REPLIES=0` 整体关掉（回到只记录）。没有配置模型时不回复。

## 9. 验收

- 群里没点名发一句，AEEIS 在同一个群里回复一条；@阿研 时阿研回复，AEEIS 不抢话；私聊里对方回复；Bot 的话不引发连锁回复。
- 同一条消息重放或进程重启，不会有第二条回复。
- 提议出现在任务板上；自动档的 Bot 提议后开出来源为 `agent` 的 Run。
- 交接：卡片先显示交接中；侧线程里留下双方的话；接受后转给对方；拒绝后留在原处；谈不拢变成阻塞并进收件箱。
- 同一件事连续失败两次，AEEIS 发起改派，只发起一次。
- 只记录档的 Bot 和外部 Agent 不说话。
