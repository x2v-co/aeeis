# Bot 当成员：一个「消息」列表

## 0. 现在已经是什么样

数据层面，「私聊」和「Bot 对话」已经是一件事（统一数据流 PR2，#177）：

- 每位 Bot 有一条对话（生活线程，`aeeis_conversations`，按主人范围 + agentId 一条）和一间「私聊」房间（`chat: direct`），两者由 `aeeis_bot_dialogues` 绑定。生产上（2026-11-26）8 位 Bot 各一条绑定，全部 `ready`，没有冲突，也没有未绑定的私聊房间。
- 往对话写消息前先检查绑定的房间可写（`BotDialogueService.conversationWrite` → `assertRoomEventWriter`），房间是这段关系的地址。
- 界面打开一间绑定的私聊房间，会直接跳到这位 Bot 的对话（`openGroup` → `openLifeThread`）；群聊里的「只讨论」回复逻辑跳过绑定的房间（`BotTeam` 的 `dialogueRoom`）。所以在私聊里 Bot 已经能开任务、跑 Run、用工具、问别的 Bot、交接。

还没统一的是**界面**：

| | 今天 |
|---|---|
| 左栏 | 「Bot」一栏（对话）和「群聊」一栏分开 |
| 绑定的私聊房间 | 不在群聊栏里，但还出现在「频道管理」和名册的房间链接里，点开再跳回对话 |
| 未读 | 没有，代码里没有任何已读记录 |
| 档案 | Bot 有「关于它」面板；人没有对应的档案页 |
| 群里请 Bot 做事 | 只能提议、等自主程度决定；没有一键把一句话交给它 |

## 1. 原则

- **Bot 尽量像人一样对待。** 名单、私聊、群聊、档案、状态、未读，人和 Bot 一样出现。
- **一段一对一关系只有一个入口。** 和一位 Bot 的一对一就是它的对话；绑定的房间只是它的地址，不单独露出来。
- **能做什么取决于「谁」，不取决于「在哪里」。** 见第 3 节。

## 2. 要做的事

### 2.1 一个「消息」列表（阶段 1）

- 左栏「Bot」和「群聊」两栏合成一个「消息」列表，按最近消息排序。每项：头像、名字、最后一句、未读数；Bot 头像角上一个小标记，名字后可显示「正在做 2 件」。
- 列表读一张存好的「聊天摘要」，每个聊天一行：`{ chatId, kind: direct|group, counterpart?, title, preview, lastActivityAt, backing: conversation|room }`。和 Bot 的一项指向对话（`backing: conversation`），群聊指向房间。
- 摘要在写入时更新，不在读列表时现算。更新摘要的只有两处：对话的每次写入都走 `ConversationStore.mutate`（消息、Bot 的回复、Run 通知都在这里），以及群聊房间的消息事件。下一节要加的「Run 到了结束或等你时写通知」也是一次对话写入，经过 `mutate` 顺带更新摘要，不另开一条更新路径。房间消息只更新群聊：Bot 之间的侧线程（房间描述为「侧线程」，`bot-team.ts` 的 `SIDE_THREAD`）和绑定的私聊房间都跳过，不建摘要、不算未读——绑定房间的内容已经通过它的对话算过一次，侧线程是两位 Bot 之间的事，结果会以 Bot 的名义回到你的对话里。不在读列表时现算的原因：今天列出对话要把每条对话连同全部消息和任务读出来解密（`ConversationStore.list`），每次刷新都这样做会随着简报变多越来越慢。摘要只存一句预览，不存正文；按主人范围存，和对话、房间同一个隐私边界。
- **摘要和对话一样加密。** 对话落盘时除了 id、主人、Bot、版本和更新时间，其余（任务标题、消息正文）都是密文（`sealConversation` / `conversationPlain`）。摘要里的标题和预览也用同一套 `sealAggregate` 加密；明文只留 id、主人范围、`kind`、`backing`、时间和条数，够排序和数未读，不露内容。已有的聊天上线时补一次摘要。
- 绑定的私聊房间不进列表，也从「频道管理」和名册的房间链接里拿掉（侧线程今天已经这样处理）。旧链接照旧跳到对话。
- **撤下的 Bot：** Bot 撤下后（`retiredAt`），服务端拒绝再往它的对话里写，交接和 Bot 之间协作也已经跳过它。它在列表里留一项只读的历史，标「已撤下」，不显示输入框，也不出现在「新建」里。
- 「新建」里选 Bot 就打开它的对话；选人建群聊。不新增给用户直接建私聊房间的入口。若要在服务端拦，只拦公开的建房接口，不能碰 `ensureDialogueRoom`（绑定靠它建房）。

### 2.2 未读（阶段 1，新功能）

今天没有已读记录，这是新做的，不是摘要顺带的。先说清现在的数据：

- Bot 在对话里的回复就是一条消息：`role: 'user'`，`speaker: { role: 'agent', id: <botId> }`（`BotDialogueService` 用 `conversations.post` 写入）。消息没有序号，只有 `createdAt`。
- 任务不存状态，读的时候从它最新的 Run 算出来。Run 结束或停下等你时，「任务「…」：succeeded」这类 `notification` 消息由 `syncNotifications` 写进对话，而它今天只在界面打开这条对话时被调用。所以一位你没打开的 Bot 早上交来简报，对话里什么都不会多，未读也就不会变。

要做的：

- **Run 状态变了就写通知：** Run 进入结束状态（succeeded、failed、cancelled）或停下等你（needs_input、needs_approval、unknown）时，服务端为它所在的对话写一条通知并更新摘要，不再依赖界面打开。下面几件事要一起做：
  - **Run 要知道自己属于哪条对话。** 今天 Run 不记对话，只有任务记着自己最新的 Run（`latestRunId`）；反过来找要把每条对话打开翻任务，和摘要要避免的开销一样。但每个 Run 已经记着自己的线程（`thread_id`），每个任务正好一个线程（`task.threadId`）。所以加一张小表「线程 → 对话、任务」，在任务的线程建出来时写一次（`ConversationService` 开 Run 前建线程的那一处；例程、私聊、群里分派开 Run 都经过它），Run 通过自己的线程找到对话。这样同一线程里的重试、后续 Run 不经过对话消息也找得到。上线时按每条对话里每个任务的 `threadId` 补一次，不只看 `latestRunId`：旧的 Run 状态也可能后来才变（例如几天前还在等批准的 Run）。这张表只存 id（线程、对话、任务、主人范围），不存标题。
  - **信号会丢，用现成的扫描器兜底。** Run 的状态在 worker 里变，保存提交后发的数据库通知（`pg_notify`）只是提示，发失败会被吞掉。代码里已经有现成的扫描器：`RunEventScanner` 按 id 一轮轮扫过所有 Run（`CollaborationTriggerPump`、`RsiProposalPump` 都用它），`pg_notify` 只让它早点扫，定时器兜住丢掉的信号。它的游标只记「这一轮扫到哪」，一轮扫完就从头再来，代码里明说游标只是调度提示、不证明处理过；用它的程序各自记下自己处理过什么（例如协作触发按策略和事件记决定）。所以 Run 通知照这个样子做：
    - **自己记下通知过什么。** 「线程 → 对话、任务」表上记一列「最后写过的通知」（Run id 和去重键，不含内容）。每一轮都会再看到所有旧 Run，先和这一列比，一样就跳过，不一样才打开那条对话写通知、再更新这一列；`followupHash` 去重仍是最后一道保险。不能靠打开每条对话比 `followupHash` 来判断，那正是摘要要避免的开销。
    - **看 Run 现在的状态，不看事件类型。** 不是每种状态都有对应的事件（有 `run.failed`、`run.cancelled`、`task.completed`、批准请求等，`needs_input`、`unknown` 没有）。扫到有新事件的 Run，就看它当前的 `status`：结束或等你、而且是线程里最新的 Run，才写。
    - **旧 Run 在上线时算作已处理，不靠时间截断。** 扫描器没有末尾，每一轮都会扫到所有旧 Run；也没有地方记着 Run 的状态是什么时候变的，`updatedAt` 每次写入都会变，不只状态变化（一个还在等批准的旧 Run 后来多写了一条事件，也会显得「刚变过」）。所以上线时补「线程 → 对话、任务」表的同时，把每个线程的「最后写过的通知」填成它现在最新的 Run 和状态：已有的都算处理过，只有上线后真的变了的才和这一列对不上、写通知。旧 Run 的通知照今天的样子，在打开那条对话时补写。否则上线当天所有从没写过通知的旧 Run 会一起冒出来，未读一下子堆满。
  - **只为每个任务最新的 Run 写通知。** 今天 `syncNotifications` 只看任务的 `latestRunId`。按线程找到对话后，同一线程里被重试、被取代的旧 Run 状态变了也会被找到，这时不写：只给线程里最新的 Run（`thread_sequence` 最大的那个，已有 `(thread_id, thread_sequence)` 索引）写，和打开对话时补写的结果一致（例如几天前还在等批准、后来又重跑过的旧 Run 不再冒出通知）。
  - **在 Run 保存之后写，不放进 Run 的事务里。** 通知用同一个 `followupHash` 去重，扫描器写的、下一轮再看到时、界面打开时补写的，写几次都只留一条。
- **什么算一条「新的」：** 看说话的人，不看消息类型。对话里没有说话人的消息（Run 通知）和说话人不是你的消息（Bot 的回复，`speaker.role` 为 `agent`）算；说话人是你的不算，包括你从飞书发来的（它们记成你的消息）、你保存的产物（`notification` 类型，但说话人是你），以及绑定房间导入的历史里你自己的那些。群聊里只有别人**新发**的话算：房间事件里 `operation` 为 `publish`、类型为 `message` 或 `canonical_response`、发出的人不是你。改写（`revise`）和撤回（`retract`）不加未读，只更新预览；`decision`、`task_update`、`system` 这类事件和系统发的事件（`actorType: system`）也不算。Run 进行中的步骤不算。
- **怎么记：** 每人每个聊天记一个「读到第几条」：摘要里「新的」累计条数在你读完时的值，存在这个人自己的范围里，只有本人能读。打开聊天并看到底部时更新；换设备、刷新后一致。
- **怎么数：** 摘要上记「新的」累计条数，只增不减，写入时加一，另记最后一条的时间用来排序。未读数 = 累计条数 − 你的「读到第几条」，封顶显示 99+。不用「读到」时间去比：摘要不存每条消息的时间，只凭一个总数和一个时间算不出读到之后又来了几条。
- **通知和预览都说人话：** Run 通知的正文改成「简报到了：<任务标题>」「等你批准：<任务标题>」「没做完：<任务标题>」这样，对话里和列表预览用同一句，不再露 `succeeded` 这类状态名；去重键不变，所以改措辞不会让旧通知再写一遍。列表预览取最后一条「新的」消息的正文开头。

### 2.3 一个档案页（阶段 1）

- 点头像打开成员档案，人和 Bot 同一个页面。Bot 多几栏（就是今天「关于它」的内容）：角色和背景、自主程度、工具、例程、和其他 Bot 的侧线程（默认折叠）。
- 今天每个工作区只有主人一个人，所以人的档案页暂时只有「你」：名字、头像、所在群聊。先把页面做成人和 Bot 共用的样子，等「加用户」时不用再改结构。

### 2.4 群里「交给它」（阶段 2）

群里发话时已经能交给一位 Bot：@ 它，或发送时选一位 Bot，这句话会记成它对话里的一条讨论（`recordRosterHandoff`），出现在任务板的「capture」列（讨论中的任务）；任务板上已有的任务还能「领取」「分派」「转交」。缺的只是**事后**交：一句已经发出去的话（人说的，或 Bot 的回复）没法再交给谁。

- 群里每句话下加「交给它」，选一位 Bot（默认是回这句话的那位）：走同一个 `recordRosterHandoff`，带上原话的 `sourceEventId`。线上它不在页面里写对话，而是请服务端把这句群消息「送达」这位 Bot（`/rooms/:id/session-events/:eventId/deliver`，`BotDialogueService.deliver`，只带 Bot 和交付方式），记成这位 Bot 对话里的一条讨论。不加新接口。
- **只能交给发话时就在场的 Bot。** `deliver` 拒绝不在这句话收件人里的 Bot（群里的 AEEIS 例外，它是每个群的入口）。所以选人只列发话时在群里的 Bot；后来才加进群的 Bot 不能接之前的话。已撤下的 Bot 也不列。
- **原话可能已经在它那里了。** 群里没点名的话，今天已经作为「intake」交给每位成员 Bot：在它的对话里记成一条**未分配**的消息（`unassigned: true`，没有任务，所以任务板上看不到）。送达的去重键是「房间 + 消息 + Bot + 交付方式」，intake 和 handoff 是不同的键，再走 handoff 会把同一句话再记一遍。对话里的消息写下后也不能改。规则：
  - 这位 Bot 还没收过这句话：照常走 handoff，记成一条新讨论（带新任务）。
  - 已经作为 intake 收过：用「改派」——追加一条消息，`correctsMessageId` 指向那条 intake，原消息不动，这句话的实际归属取最新一次改派（`ConversationService` 已经这样算）。这一步只能在服务端 `deliver` 里做：页面只知道群消息，不知道它在 Bot 对话里变成了哪条消息；服务端从已完成的 intake 送达记录（`targetId`）拿到它。所以 `deliver` 收到 handoff 时，先看同一句话、同一位 Bot 有没有已完成的 intake；有就改派那条消息，没有就照旧新记。
  - 今天改派只能指向**已有**任务（`validateCorrection` 要求 `taskIds`、拒绝 `newTask`），而任务只能随一条消息新建，所以还要放宽一处规则：**被改派的消息目前仍未分配时，改派可以带 `newTask`**，新建一条讨论任务。「仍未分配」看这句话现在的归属：原消息是未分配的，而且没有后来的改派已经把它归到任务；否则直接调接口的人可以对同一句话改派两次、建出两个任务。其余限制不变：原消息必须是没执行过的讨论消息，改派不能开工（`intent: discuss`）。
  - 生成的是真正的讨论任务，任务板的讨论列自然看得见，不用改任务板，同一句话也不会在对话里记两遍。服务端改两处：`deliver` 和 `validateCorrection`，约几十行加测试，在阶段 2 做。
  - 去重：沿用送达本来的键（交付方式为 handoff），不另加。发话时就选过这位 Bot 的，用的也是 handoff，事后再点「交给它」拿回同一个任务。AEEIS 发话时记的是「entry」，所以对 AEEIS 点「交给它」时，已有的 entry 送达也算已经交过，不再建第二个任务。
- 记成讨论就是「记下来，未执行」，是否开工由它的自主程度决定，不在群里直接开出权限更大的 Run。服务端的「每位 Bot 最多 3 件进行中」只管「分派」「转交」，不管新记的讨论，这里也不另加。
- 记在点的人名下，用点的人的范围和额度；任务板和这位 Bot 的对话都看得见。同一句话对同一位 Bot 只有一个讨论任务，不论点了几次、之前是不是 intake。

## 3. 权限：问三件事

一次 Bot 的动作是否允许、结果给谁看，只看：

1. **谁在请它做。** Run 记在请求人的范围里，用请求人的额度。
2. **Bot 被允许做什么。** 主人给它的工具授权、自主程度和常驻嘱咐；请求人不能加权限。
3. **在哪里说的，决定谁看得见。** 对话里只有两方；群里按房间成员和隐私设置。

今天只有主人自己能用自己的 Bot，三件事落在同一个人身上。别人用你的 Bot 见第 6 节。

## 4. 不做的事

- 不迁数据、不归档绑定的私聊房间：房间是绑定的地址，归档后它变成只读，对这位 Bot 的每一次写入都会被拒绝。
- 不复制历史：绑定建立时已经整理过房间历史（`aeeis_bot_dialogue_operations` 已完成）。
- 不改群聊的回复规则、交接、改派、任务板。
- 不做人和人的私聊（今天每个工作区只有主人一个人）。
- 飞书私信照旧写进和 AEEIS 的对话。

## 5. 阶段

| 阶段 | 内容 | 风险 |
|---|---|---|
| 1a | 聊天摘要和未读：新存储；在对话写入（`mutate`）和群聊房间消息两处更新（跳过侧线程和绑定房间）；「线程 → 对话、任务」小表，带「最后写过的通知」一列；Run 状态变化时为线程里最新的 Run 写通知（用现成的 `RunEventScanner` 一轮轮扫，`pg_notify` 催、定时兜底；表上记「最后写过的通知」用来跳过；上线时把已有的都记成处理过），通知说人话；已有聊天和 Run 补一次 | 中：新的数据和写入路径，worker 和 API 两边都要动 |
| 1b | 「消息」列表 + 同一个档案页；绑定房间从频道管理和名册里隐去 | 低：只动界面，读 1a 的摘要 |
| 2 | 群里「交给它」：对已发出的话复用 `recordRosterHandoff`；收过 intake 的由服务端 `deliver` 改派那条消息，并放开「改派仍未分配的消息时可新建任务」；只列发话时在场的 Bot | 低：不加新接口，改 `deliver` 和一处校验 |
| 3 | 别人也能和你的 Bot 说话（第 6 节，单独设计） | 高，跟「加用户」一起做 |

## 6. 以后：别人和你的 Bot 说话（单独设计）

今天做不到，不是差一张表：对话和 Bot 都按主人范围存，绑定服务对非主人直接返回「Unknown Bot」。要让别人用，需要单独设计：

- Bot 的常驻嘱咐、记忆、工具授权在主人范围里，Run 记在请求人范围里——跨范围读哪些、写哪些。
- 每个请求人和这位 Bot 各一条对话，存在谁的范围里；主人能看到什么（用量，不看内容）。
- 已定：主人可以另设「对别人开放的工具」，默认只读；不在其中的工具被拒绝并说明原因。

这部分和「加用户」、隐私页一起写成单独的设计文档。

## 7. 验收（阶段 1、2）

- 左栏只有一个「消息」列表，Bot 和群聊混排；能看出谁是 Bot；一位 Bot 只有一项。
- 频道管理和名册里不再出现绑定的私聊房间；旧房间链接打开对应的对话。
